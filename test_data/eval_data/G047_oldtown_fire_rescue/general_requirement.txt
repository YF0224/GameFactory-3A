## 1. 定位与完整流程 [S01–S06]

- S01 类型：3D 第三人称单建筑火场救援。本测例包含的能力：冻结火场布局、离散火势传播与烟雾、水量预算与喷射、破拆开路、三名被困者状态机与背负救援、路线阻断提示、开场/首救/结算视频。
- S02 核心循环一句话：进入火场 → 控火开路 → 救出被困者 → 抵达出口 → 结算。
- S03 流程：任务开始（建筑外）→ 进入火场 → 控火/破拆推进 → 逐一救出被困者 → 携全员抵达出口 → 结算。
- S04 最低完整流程：任务开始、可操作移动与喷射、3 名被困者、出口撤离、结算、重开必须全部存在且有真实入口。
- S05 失败恢复入口：失败结算一键重开（火场按 seed 复现）；Esc 暂停。
- S06 本局耦合边速览：灭火资源系统→火势系统（水量消耗熄灭火格改变火格集合）；火势系统→烟雾与玩家状态（烟雾限制视野/移速并扣 HP）；火势系统→被困者状态（火/烟逼近触发呼救与恐慌）。

## 2. 完整核心循环与阶段 [S06–S11]

完整循环：启动与任务开始 → 进入火场 → 控火/破拆推进 → 逐一救出被困者 → 携全员抵达出口 → 结算 → 重开/返回。每阶段六要素如下（引用本 spec §3–§7 与 §9 对应规则）：

- S06 启动与任务开始
  - input：系统启动加载完成（触发方：系统）；玩家按 Enter/点击「出警」
  - precondition：构建可启动且火场按 seed=1047 生成完成
  - state_change：进入「任务开始」状态（建筑外整备位）；首次进入按 §10 C01 触发开场视频
  - feedback：任务简报（3 名被困者、水量 100、限时 300 秒）
  - next_actions：进入「火场推进」
  - outcome：无跨局状态写入（见 §7 V04）
- S07 进入火场
  - input：WASD 移动、左键喷射、E 背起/放下、F 破拆、Esc 暂停（触发方：玩家）
  - precondition：玩家越过建筑入口判定
  - state_change：进入火场内推进状态；火势与烟雾按 G03 时间步推进
  - feedback：火焰/烟雾/热浪表现按 §9 F05 呈现
  - next_actions：控火与破拆开路
  - outcome：火格集合与被救状态局内推进
- S08 控火/破拆推进
  - input：左键喷射／F 破拆（触发方：玩家）
  - precondition：水量 >0（喷射）；相邻格为倒塌物（破拆）
  - state_change：火格累计 20 单位熄灭；倒塌物 2 秒清除；路径可达性更新
  - feedback：喷水水雾、余烬、坍塌预警（§9 F05）
  - next_actions：抵达被困者位置
  - outcome：资源消耗与火格集合变化可对账
- S09 逐一救援
  - input：E 背起被困者（触发方：玩家）
  - precondition：与被困者距离 ≤ 交互半径（任意状态可背起）
  - state_change：被困者转为「背负中」；玩家移速减半、禁喷射
  - feedback：背负图标、呼救声随状态停止
  - next_actions：背至出口外放下 → 该被困者获救
  - outcome：已救人数 +1（事件可核）
- S10 携全员抵达出口
  - input：移动至出口判定（触发方：玩家/系统）
  - precondition：3 名被困者全部获救（在出口外）
  - state_change：触发 V01 胜利 →「结算」（先播 C03）
  - feedback：全员撤离横幅与结算面板
  - next_actions：重开或返回
  - outcome：按 V01 结算
- S11 结算与判负
  - input：Enter＝重开 / Esc＝返回（触发方：玩家）；伤亡 2 人／HP 归零／300 秒超时（触发方：系统）
  - precondition：V01 或 V02 达成
  - state_change：进入「结算/判负」状态；模拟冻结
  - feedback：结算显示用时、剩余水量、伤亡数；判负注明原因
  - next_actions：重开（seed 复现）或返回
  - outcome：无跨局写入

## 3. 数值口径与全局规则 [G01–G07]

- G01 统一刻度：格子制建筑平面；时间用游戏模拟秒（暂停冻结）；HP 与水量为整数。
- G02 数值（本包冻结值）：玩家 HP 100；接触火格每秒 −10、烟雾区每秒 −2、安全区每秒 +1（上限 100）；被困者 3 名各有 HP 50（接触火格每秒 −10）；伤亡上限 1 人（第 2 人伤亡即判负）；水箱 100 单位、每秒喷射 10 单位、每熄灭一火格耗 20 单位；破拆倒塌物耗时 2 秒。
- G03 火势传播（本包冻结值）：火格每 4 秒尝试向相邻格蔓延——邻格为木质则点燃、为水泥/金属则不燃；烟雾格由火格生成并向邻格缓慢扩散。状态转移 oracle：给定 seed=1047 的初始火格集合（单一木质火格），第 4 秒其相邻木质格必被点燃、水泥格不燃，火格集合随时间步唯一确定；任何偏离即 FAIL。水量守恒 oracle：喷射熄灭 5 个火格必耗 100 单位（20/格）。
- G04 seed 与计时：fixed_seed=1047 冻结初始火格、可燃材质分布、被困者位置与烟雾扩散；单局限时 **300 秒**（超时判负）。
- G05 暂停与失焦：Esc 暂停冻结火势、烟雾、HP 与计时；窗口失焦自动暂停；UI 过渡不推进状态。
- G06 被困者状态机（本包冻结值）：每名被困者状态＝平静 calm → 呼救 calling（火格或烟雾格与其距离 ≤2 格时触发）→ 恐慌 panicked（自身 HP <30 或身处烟雾格）→ 昏迷 down（HP 归零）；昏迷后 10 秒内未被背起即计伤亡；呼救与恐慌伴随头顶图标（文字标签「呼救中/恐慌」）与呼救音效；任意状态均可被 E 背起；背至出口外＝获救 rescued；状态转移为单向（获救终态除外）。
- G07 烟雾移速与路线阻断（本包冻结值）：玩家处于烟雾格时移速 ×0.7（叠加背人减半时取乘积 ×0.35）；路线阻断判定——系统每次火格/倒塌物变化后计算每名未获救被困者到出口的通路，若全部通路被「火格＋未清除倒塌物」封锁，则 HUD 高亮提示「路线阻断」并指示最近可清理倒塌物（不自动开路）；判负条件不变（G02/G04）。

## 4. 操作与输入 [I01–I07]

- I01 键鼠：WASD＝移动；左键按住＝喷射灭火（朝向前方 2 格锥形）；E＝背起/放下被困者；F＝破拆相邻倒塌物；Esc＝暂停；结算界面 Enter＝重开。
- I02 输入语义边界：水量为 0 时喷射无效；非倒塌物前按 F 无效；背人时移速减半且不能喷射；暂停/结算期间输入无效。
- I03 无手柄需求。
- I04 输入优先级：暂停与结算状态阻断全部玩法输入；同帧多输入按移动→喷射→破拆→背放顺序结算。
- I05 焦点与失焦规则：点击画布捕获输入焦点；面板层阻断点击穿透；窗口失焦自动暂停。
- I06 UI 必须显示的状态：HP、水量、剩余时间、已救人数/3、被困者状态图标（呼救/恐慌/昏迷）、路线阻断提示；HUD 对照见 rubric。
- I07 输入延迟目标：移动/喷射按键到画面反馈 ≤ 80 毫秒；背起/破拆交互反馈 ≤ 100 毫秒。

## 5. 建筑与内容清单 [L01–L04]

- L01 生成对象：玩家消防员 1（人形）、被困者 3（原创造型：修表匠老人/杂货店员/学徒少年）、火格与烟雾格若干、倒塌物 4 处、出口 1；建筑装饰为表现层。
- L02 建筑：单栋老城砖木混合建筑（约 20×16 格两层平面：门厅、走道、三间房、后院出口）；初始火格 3 处、可燃材质分布与被困者位置由 seed=1047 冻结。
- L03 目标物/交互物/场景/UI 对象：本 spec §3–§9 引用的界面元素（任务简报/HUD/结算/判负/暂停/视频播放层）与交互物逐类存在且运行时可进入；数量与属性以 L01/L02 与 G 系为准。
- L04 冻结需求 vs 实现默认 vs 生成自由度：本 spec 明确写出的数值与数量为冻结需求；§9 未冻结的装饰造型与配色为生成自由度，不得评估为缺失；实现默认值必须明确标注且符合核心机制。

## 6. 机制系统 [M01–M05]

- M01 离散火势传播（主机制）
  - input：系统计时（seed 驱动）
  - precondition：处于游玩状态（非暂停/结算）
  - state_change：火格每 4 秒向相邻可燃格蔓延（按 G03 规则与材质表）；烟雾由火格生成并向邻格扩散
  - observable：火格点燃/熄灭事件与逐时间步火格集合快照（规则可复现）
  - invalid_case：不可燃材质格永不点燃
  - recovery：灭火（M03）改变集合
- M02 烟雾能见度与移动
  - input：进入烟雾区（系统）
  - precondition：玩家或烟雾格位置更新
  - state_change：能见度下降（视野半径受限）＋ HP 每秒 −2 ＋ 移速 ×0.7（G07）
  - observable：能见度状态与玩家移动轨迹相关性（采样）
  - invalid_case：离开烟雾区即恢复
  - recovery：灭火减少烟雾源
- M03 灭火资源
  - input：左键喷射
  - precondition：水量 >0
  - state_change：水量按 10 单位/秒消耗 → 命中火格累计 20 单位后熄灭；资源有限需取舍
  - observable：灭火事件与水量流水（守恒，见 G03 oracle）
  - invalid_case：水量 0 喷射无效
  - recovery：无补给（单局预算制）
- M04 障碍清理与路线阻断
  - input：F 破拆
  - precondition：相邻格为倒塌物
  - state_change：2 秒清除倒塌物 → 路径开通；每次火格/倒塌物变化后重算路线阻断并更新提示（G07）
  - observable：路径可达性变化事件与「路线阻断」提示事件
  - invalid_case：非倒塌物前按 F 无效
  - recovery：破拆开路即解除阻断
- M05 被困者状态与救援
  - input：火/烟逼近（系统）／E 背起放下（玩家）
  - precondition：状态机按 G06 转移；背起需距离 ≤ 交互半径
  - state_change：calm→calling→panicked→down 单向转移；背起 → 背负中（移速减半、禁喷射）；出口外放下 → rescued
  - observable：`npc_state` 事件（含 NPC ID、前后状态）、呼救音效与头顶图标、`rescued` 事件
  - invalid_case：昏迷 10 秒未背起 → 计伤亡；伤亡达 2 → 判负（V02）
  - recovery：任意状态可背起救援（昏迷期 10 秒内）

系统耦合边（玩法必需、可复现）：

- E01 from_system=灭火资源系统 → to_system=火势系统；changed_state=喷射熄灭火格使火格集合缩小、蔓延起点减少；验证方式=熄灭前后第 4 秒火格集合快照对照（state_before/after）。
- E02 from_system=火势系统 → to_system=烟雾与玩家状态系统；changed_state=火格生成烟雾格 → 玩家视野/移速（×0.7）与 HP 消耗（−2/秒）联动变化；验证方式=火格旁/无火区两态 HP 流水与移速采样。
- E03 from_system=火势系统 → to_system=被困者状态系统；changed_state=火/烟与被困者距离 ≤2 格触发 calling、烟雾格或 HP<30 触发 panicked；验证方式=火/烟逼近前后 npc_state 事件对照。

## 7. 成功、失败与恢复 [V01–V05]

- V01 成功条件：3 名被困者全部救出并随玩家抵达出口 → 结算（显示用时、剩余水量、伤亡数）。
- V02 失败条件：被困者伤亡达 2 人、玩家 HP 归零、或 300 秒超时 → 失败结算（注明原因）。
- V03 恢复语义：失败结算一键重开；火场按 seed 复现（初始火格、材质、被困者位置与烟雾扩散一致）；局内无存档。
- V04 persistent_state：无（重开全量清空；局内火场状态仅本局推进）。
- V05 persistent_state 生命周期：当前动作级状态即时结算；当前局级状态（火格/被救/伤亡）局内保留、重开清空；无跨局保留状态。
- V06 软锁与不可达处理：不设永久软锁——路线阻断提示引导清理倒塌物或控火开路；玩家死亡/超时走 V02 判负路径而非无限等待。

## 8. 世界设定与创作基线 [W01–W08]

- W01 世界与时代背景：近现代的「青槐老城」，冬夜木楼电路老化起火，老城义务消防队第一时间抵达。
- W02 场景所在地：青槐老城的「德昌号」杂货楼——门厅、走道、三间房与后院出口的砖木混合两层建筑。
- W03 玩家身份与当前任务：玩家是义务消防队队员；当前任务：控火、破拆、救出楼内 3 名被困居民并全员撤至后院出口。
- W04 失败代价与结局表达：伤亡超限/自身倒下/超时＝救援失败（判负文案按原因）；成功则 C03 呈现全员撤出、火势渐熄的老街夜景。
- W05 叙事来源：三名被困者各有身份与位置来源——修表匠老人困于里间工作台、杂货店员困于柜台后储物间、学徒少年困于阁楼楼梯口；倒塌物＝烧塌的梁架与货架；水箱＝背负式水罐。全部原创。
- W06 视觉风格与色彩材质：风格化写实夜景火场；主色＝炭黑（#1F1B18 系）＋火橙红（#E0562A 系）＋水雾青白（#9FB8C4 系）；材质以焦木、砖石、水渍反光为主；火光为唯一主光源方向。
- W07 环境氛围与声音语言：夜火中的老街——常驻热浪低鸣与远处警铃；音效语言为「火焰噼啪＋水雾嘶声＋呼救人声＋警报」，全部音效按 §9 F06 冻结清单交付。
- W08 故事表达方式：开场视频（C01）交代灾情 → 首名获救视频（C02）作为正反馈节点 → 结算视频（C03）收束；故事只做包装，不改变机制数值。

## 9. 演出、镜头与反馈 [F01–F10]

- F01 视角与镜头：第三人称斜后方跟随（距离 3.5 米、高度 2 米），平滑插值 0.08 秒；镜头边界＝建筑墙体相机碰撞体；重开后镜头回建筑外整备位；烟雾中镜头轻微低频晃动（幅度 0.02 米）。
- F02 关键操作镜头变化：坍塌预警 0.2 秒中幅震动；玩家受击 0.15 秒小幅震动＋红闪；背起被困者时镜头轻微下移 3°；无慢动作。
- F03 输入与延迟：见 I07。
- F04 环境常驻效果：火焰跳动与余烬上飘、烟雾体积滚动、窗外夜雨微光、出口绿色安全灯；火焰为动态光源。
- F05 事件反馈表（事件 → 表现 → 结束条件，全部为冻结需求）：

| 事件 | 画面表现 | 音效 | 结束条件 |
|---|---|---|---|
| 喷射灭火 | 前方 2 格锥形水雾＋火格蒸汽白烟 | 水压嘶声（按住循环） | 松开或水量 0 |
| 火格熄灭 | 火焰收缩熄灭＋余烬灰烟 | 熄灭嘶声 | 完成 |
| 火势蔓延 | 新火格点燃闪光＋火星迸溅 | 木质爆裂声 | 点燃完成 |
| 烟雾扩格 | 烟雾体积推移＋视野边缘变灰 | 烟雾低鸣（烟雾区循环） | 离开或通风 |
| 破拆进行 | 倒塌物碎屑飞溅＋进度环 2 秒 | 锤击闷响×2 | 清除完成 |

## 生成任务明确性补充（2026-10-12）

> 本补充只约束游戏生成输入，不引用 rubric。所有生成器必须以本文件规则和下列 JSONL 任务为准；未列出的装饰细节可以自由发挥，但不得省略已列资产或生命周期。

### 故事与流程最低合同
- **玩家身份与当前冲突**：以 §1、§8 的角色/世界/冲突为唯一叙事入口；开局必须让玩家知道“我是谁、现在要解决什么问题”。
- **阶段性目标**：必须有可操作的阶段目标、至少一次状态变化/升级，并在 §7 的胜利、失败、重开入口中闭环；不能只生成一个无结果的场景演示。
- **结果承接**：胜利/失败都要有明确结果文案或演出，并回到可重开、暂停或标题入口；视频、音频和 VFX 不得推进未完成的玩法状态。

### 生成任务清单（JSONL 冻结口径）
- scene：1 个；必须生成连贯可游玩的空间，不得出现下半部文字、拼贴面板、物体 lineup 或 UI。
- object：5 个（text-to-3D 4，image-to-3D 1）；object 任务资产为：volunteer_firefighter, watchmaker_elder, grocery_clerk, apprentice_boy, collapsed_beam。每项只允许一个物体；组合物必须拆成独立任务。
- motion：4 个；覆盖动作：idle, run, carry_npc, demolish_swing。
- video/audio/mechanic/UI：分别为 3/11/1/1 个任务；若某项为 0，只能是本案例明确的 N/A，不得默默遗漏。

### Video / motion / audio 生命周期
- Video 每项必须写清 `trigger`、`start_condition`、`duration_sec`、`skippable`、`skip_behavior`、`end_condition` 和进入的下一个游戏状态；播放期间不得偷偷消耗计时或改变战斗/任务数值。
- Motion 每项必须写清 `source_asset`、`trigger`、`start_condition`、`duration_sec`、`loop`、`end_condition` 和 `cancel_behavior`；动作要与对应输入/机制事件绑定，不可只写“walk animation”。
- Audio 每项必须写清触发事件、时长、`loop`、`stop_condition`、优先级和 ducking；关键命中/提示音必须与事件帧同步，暂停/结算时按 §9 处理。

### Mechanic / UI / 游玩手感
- Mechanic JSON 与 §1–§7 配对：每个输入都要有 precondition、state_change、feedback、next_state；必须说明失败/禁用分支。
- UI JSON 与 §9/F10 配对：HUD、菜单、结算、暂停、错误/禁用态要有 state binding；关键状态不能只用颜色表达。
- 手感冻结：相机跟随/构图、FOV、碰撞/遮挡、镜头调整与镜头震动必须在 §9 说明；震动反馈必须写明触发、强度和持续时间，并提供关闭设置且不改变判定。

### VFX 时机合同
每个特效必须写清 `trigger event`、预备/前摇、active window、持续时间、结束条件、被打断/取消条件，以及和相机震动、音效、UI 的同步关系；命中特效、失败特效、胜利特效不能只写“有粒子”。
