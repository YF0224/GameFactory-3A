## 1. 定位与完整流程 [S01–S05]

- S01 类型：回合制自动战斗布阵（固定对手脚本对局）。
- S02 核心循环一句话：准备期招募/刷新/上阵 → 战斗期自动交战 → 结算金币 → 下一轮。
- S03 流程：准备期（30 秒）⇄ 战斗期（自动，时限 30 秒）交替，共 **8 轮**；任意轮一方血量归零即提前终局。
- S04 最低完整流程：招募/刷新/出售界面、上阵棋盘与备战席、自动战斗、轮结算、终局结算、重开必须全部存在且有真实入口。
- S05 失败恢复入口：己方血量归零 → 失败结算一键重开（对局全量重置）；Esc 暂停准备期。

## 2. 完整核心循环与阶段 [S06–S13]

完整循环：主菜单 → 开始对局 → 准备期 ⇄ 自动战斗期 → 轮结算（共 8 轮循环）→ 终局结算；准备期可 Esc 暂停；一方血量归零即时进入对应结算。每阶段六要素如下（引用本 spec §3–§7 对应规则）：

- S06 主菜单
  - input：系统启动，玩家确认进入
  - precondition：程序启动完成
  - state_change：显示主菜单（开始/退出）
  - feedback：主菜单界面
  - next_actions：玩家点击「开始」→ S07
  - outcome：无状态副作用
- S07 开始对局
  - input：玩家点击「开始」
  - precondition：主菜单已显示
  - state_change：对局初始化：金币 5（第 1 轮开局）、己方血量 20、对手血量 20、轮号 1、备战席 8 格清空
  - feedback：HUD 显示初始值（见 §4 I06）
  - next_actions：进入 S08 准备期
  - outcome：无跨局状态（见 §7 V05）
- S08 准备期（每轮 30 秒）
  - input：玩家招募/刷新/出售/拖拽上阵/换位（按 §4 I01/I02 键位）；30 秒倒计时归零（系统）
  - precondition：轮号已确定且未超 8；上阵数 ≤ 上限（轮次＋2，最多 8）
  - state_change：招募/刷新/出售即时结算；合成与羁绊随阵容即时重算
  - feedback：商店、备战席与羁绊提示；倒计时显示
  - next_actions：倒计时归零 → S09 自动战斗期；Esc → S11
  - outcome：阵容/金币/备战席跨轮保留
- S09 自动战斗期（时限 30 秒）
  - input：系统交战调度（按 §3 G02/G05 规则）；玩家不可操作
  - precondition：准备期结束
  - state_change：双方单位按站位、射程与间隔自动交战；侦察蜂开战跳至敌方后排；至一方全灭或 30 秒时限到点
  - feedback：战斗表现与特效（见 §9 F05）
  - next_actions：一方全灭或时限到点 → S10 轮结算
  - outcome：战斗事件流确定性落盘
- S10 轮结算
  - input：系统结算
  - precondition：战斗结束（全灭或超时判定）
  - state_change：战败方扣血 2＋对方存活单位数；轮结算入账＝基础收入 5＋利息（存金 10% 向下取整，上限 5）＋连败补偿（连败第 n 轮额外 +n 金，上限 3）＋胜利加成（胜一轮 +1 金）；轮号 +1
  - feedback：胜负横幅与金币飞字（见 §9 F05）
  - next_actions：轮号 ≤ 8 → 回 S08；一方血量归零 → S12/S13
  - outcome：进度推进；状态保留
- S11 暂停
  - input：玩家按 Esc
  - precondition：处于 S08 准备期
  - state_change：冻结倒计时与商店
  - feedback：暂停菜单（继续/重开/返回菜单）
  - next_actions：Esc 或「继续」→ 返回准备期；「重开」→ S07；「返回菜单」→ S06
  - outcome：恢复后无副作用
- S12 胜利结算
  - input：系统结算
  - precondition：对手血量归零（任意轮）或 8 轮结束时己方血量 > 0 且 ≥ 对手（见 §7 V01）
  - state_change：显示胜利结算（剩余血量与金币）
  - feedback：胜利全屏特效（见 §9 F05）
  - next_actions：Enter 重开 → S07；返回菜单 → S06
  - outcome：按 §7 V01/V03 判定并结算
- S13 失败结算
  - input：系统结算
  - precondition：己方血量归零（见 §7 V02）
  - state_change：显示失败结算
  - feedback：失败反馈
  - next_actions：Enter 一键重开 → S07；返回菜单 → S06
  - outcome：按 §7 V02/V03 判定并结算（全量重置）

## 3. 数值口径与全局规则 [G01–G06]

- G01 统一刻度：金币/HP/伤害为整数；棋盘 6×4 格（每方 3×4 上阵区）＋备战席 8 格；上阵上限＝轮次＋2（最多 8）。
- G02 单位池与交战规则（本包冻结值）：前排——巡逻兵（招募 3 金、HP 200、攻 20、甲 10、攻击间隔 1.0 秒、移速 2 格/秒）、装甲哨（3 金、HP 300、攻 15、甲 20、间隔 1.0 秒、移速 2）；后排——狙击手（3 金、HP 100、攻 40、甲 0、射程 4、间隔 1.2 秒、移速 1.5）、医疗无人机（3 金、HP 80、攻 0、甲 0、治疗 15、射程 3、间隔 1.5 秒、移速 1.5）；特种——破甲者（3 金、HP 150、攻 30、甲 0、命中无视甲、间隔 1.0 秒、移速 2）、侦察蜂（3 金、HP 60、攻 10、甲 0、间隔 0.8 秒、移速 3；**开战时立即跳至敌方上阵区后排最近空格**）。伤害＝攻 −甲，**最低 1 点**（破甲者无视甲）；医疗＋15。索敌＝攻击射程内最近的敌方单位（射程按格中心欧氏距离 ≤ 射程；近战射程 1），等距取单位 ID 较小者；同一时刻多个行动按单位 ID 升序结算。
- G03 羁绊与合成（本包冻结值）：羁绊仅一条——上阵同排 2 前排单位 →「哨卫」全体前排 HP +10%（随阵容即时重算）。合成：3 个同名一星单位（**场上或备战席任意位置**）自动合成二星（HP 与攻 ×1.8，占 1 格；本题只做到二星）。
- G04 轮转经济（本包冻结值，方案 b 恢复全部经济机制）：第 1 轮开局 5 金；每轮结算收入＝基础 **5 金**＋**利息**（当前存金的 10% 向下取整，上限 5）＋**连败补偿**（连败第 n 轮额外 +n 金，上限 3）＋**胜利加成**（该轮战斗胜利 +1 金）；招募 3 金/单位、刷新商店 2 金/次、出售返还 2 金/单位。经济 oracle 数例：开局 5 → 招募 1 巡逻兵（−3）余 2 → 刷新（−2）余 0 → 轮结算（若存金 20 则利息 2；若连败第 2 轮则补偿 +2；若胜则 +1）；任何偏离即 FAIL。
- G05 血量、时限与复现（本包冻结值）：双方血量 20；战败方每轮扣血 **2＋对方存活单位数**（存活单位于战斗结束时统计；8 轮内双方血量可归零——连败 3 轮且对方存活 ≥5 时单轮扣 ≥11）；**可失败口径**——对手血量归零（任意轮）即胜，或 8 轮结束时己方血量 > 0 且 ≥ 对手即胜，己方血量 < 对手判负，己方归零即时判负。**战斗时限 30 秒**：超时按双方剩余单位总 HP 判定（高者胜；相等为平局，双方各扣 2＋对方存活单位数）。fixed_seed=1032 冻结商店刷新序列；**自动战斗确定性**——同 seed 同阵容同站位双跑战斗事件流 diff=0。
- G06 对手阵容表（本包冻结值，强度递增；站位＝前排单位置于对手上阵区第 1 行、后排置于第 2 行，均自左向右居中排列）：
  - 轮 1：巡逻兵 ×2
  - 轮 2：巡逻兵 ×3
  - 轮 3：巡逻兵 ×2＋狙击手 ×1
  - 轮 4：装甲哨 ×2＋狙击手 ×1
  - 轮 5：装甲哨 ×2＋狙击手 ×1＋医疗无人机 ×1
  - 轮 6：装甲哨 ×2＋狙击手 ×2＋医疗无人机 ×1
  - 轮 7：装甲哨 ×2＋狙击手 ×2＋医疗无人机 ×1＋破甲者 ×1
  - 轮 8：装甲哨 ×2（其中 1 个为二星）＋狙击手 ×2＋医疗无人机 ×1＋破甲者 ×1

## 4. 操作与输入 [I01–I06]

- I01 键鼠：点击商店单位＝招募；R＝刷新商店；拖拽单位＝上阵/换位/下阵（上阵区⇄备战席）；点击己方单位＋出售钮＝出售（返还 2 金）；准备期结束自动进入战斗；Esc＝暂停；结算界面 Enter＝重开。
- I02 输入语义边界：金币不足招募/刷新无效；上阵数达上限（轮次＋2，最多 8）后不可再上阵；备战席满 8 格且无法安置时招募无效；战斗期不可操作；暂停/结算期间输入无效。
- I03 无手柄需求。
- I04 输入优先级：暂停与结算状态阻断全部玩法输入；面板打开时玩法键不串入（沿用原 I02 口径）；同帧多输入按 §6 各机制声明的顺序结算。
- I05 焦点与点击穿透规则：点击画布捕获输入焦点；面板层阻断点击穿透；窗口失焦自动暂停，不推进游戏模拟。
- I06 UI 必须显示的状态：金币、双方血量、轮号、准备期倒计时与战斗剩余时限（按 §3 G01/G05 刻度）；备战席占用数与上阵上限（轮次＋2）；哨卫羁绊激活状态；连败计数与利息预告。
- I07 输入延迟目标：拖拽到落位反馈 ≤150 毫秒（WebGL 口径，P95，≥30 次采样/类别）。

## 5. 对局与内容清单 [L01–L04]

- L01 生成对象：六种单位（原创造型，一星与二星形态可区分）、商店 5 槽、棋盘 6×4、备战席 8 格、双方血量条；星港场景装饰非冻结需求。
- L02 对局：8 轮固定对手阵容（见 §3 G06）；商店刷新序列由 seed=1032 冻结。
- L03 目标物/交互物/场景/UI 对象：本 spec §3–§7 引用的界面元素（菜单/HUD/结算面板/商店/出售）与交互物逐类存在且运行时可进入；数量与属性以对应 G·M 条目为准。
- L04 冻结需求 vs 实现默认 vs 生成自由度：本 spec 明确写出的数值与数量为冻结需求；未给数值的表现层（装饰造型、配色、粒子）为生成自由度，不得评估为缺失；实现默认值必须明确标注且符合核心机制。音效为冻结需求（F06 清单逐条交付，缺失按 FAIL 计，T6 裁决）。

## 6. 机制系统 [M01–M04]

- M01 阶段轮转（主机制）
  - input：准备期 30 秒倒计时（系统）
  - precondition：轮号 ≤ 8；上阵数在限内
  - state_change：准备期→自动战斗期（时限 30 秒）→轮结算→下一准备期，按 G05 轮数推进与终局判定
  - output：按 §3 G05 结算轮次与终局
  - observable：phase 事件（prepare/battle/settle）与轮号流水
  - invalid_case：轮号 >8 无下一轮；战斗期玩法输入无效
  - recovery：失败/中断/非法态后的恢复按 §7 V03 恢复语义与 V04 软锁处理执行，不产生冻结规则之外的副作用
- M02 轮转经济
  - input：招募/刷新/出售（玩家）；轮结算（系统）
  - precondition：金币 ≥ 相应花费（招募 3/刷新 2）；出售目标为己方单位
  - state_change：开局 5 金；轮结算收入＝基础 5＋利息（存金 10% 向下取整上限 5）＋连败补偿（连败第 n 轮 +n，上限 3）＋胜利加成（+1）；招募 −3、刷新 −2、出售 +2
  - output：按 §3 G04 结算
  - observable：金币流水对账（见 G04 oracle）
  - invalid_case：金币不足招募/刷新被拒且不扣
  - recovery：按 §7 V03/V04 执行
- M03 合成与羁绊
  - input：阵容变化（招募/上阵/换位/出售）
  - precondition：场上或备战席任意位置存在 3 个同名一星单位（合成）；上阵同排 2 前排单位（哨卫）
  - state_change：自动合成二星（HP/攻 ×1.8、占 1 格）；哨卫全体前排 HP +10% 即时重算
  - output：按 §3 G03 结算属性差分
  - observable：合成/羁绊事件与属性差分快照
  - invalid_case：不足 3 同名不合成；下阵后羁绊即时消失；无相邻位置要求
  - recovery：按 §7 V03/V04 执行
- M04 自动战斗
  - input：战斗期开始（系统）
  - precondition：准备期结束
  - state_change：双方单位按站位、射程、间隔与索敌规则自动交战；侦察蜂开战跳敌方后排；至一方全灭或 30 秒时限（超时按剩余总 HP 判定，平局双方扣血）
  - output：按 §3 G02/G05 结算伤害与判定
  - observable：确定性战斗事件流（同 seed 双跑 diff=0）、时限与超时判定事件
  - invalid_case：射程外不交战；伤害最低 1 点；医疗不造成伤害
  - recovery：按 §7 V03/V04 执行

## 7. 成功、失败与恢复 [V01–V05]

- V01 成功条件：任意轮对手血量归零，或 8 轮结束时己方血量 > 0 且 ≥ 对手 → 胜利结算（显示剩余血量与金币）。
- V02 失败条件：己方血量归零（每败一轮扣 2＋对方存活单位数，连败若干轮可达）任意轮即时判负，或 8 轮结束时己方血量 < 对手 → 失败结算。
- V03 恢复语义：结算界面一键重开；阵容、金币、血量、备战席、商店序列按 seed 全量重置。
- V04 软锁与不可达处理：无永久软锁——关键目标均可通过正常操作达成，或触发 V02 失败路径进入结算；结算界面重开为最终恢复出路；判定不可达时按 V02 失败语义结算而非无限等待。
- V05 persistent_state 生命周期：当前动作级状态即时结算；当前局级状态（阵容/金币/血量/轮次/备战席）局内跨轮保留、重开清空；无跨局保留（重开全量清空）。

## 8. 世界设定与创作基线 [W01–W08]

- W01 世界与时代背景：环轨纪元的星港「灯泊港」每年举办候补队轮换赛——各防区候补小队以自动布阵在同一甲板上轮转对抗，胜者接管外环航道防线。
- W02 场景所在地：星港候补甲板——6×4 棋盘（每方 3×4 上阵区）、下方备战席 8 格与商店条、边缘货柜与航道舷窗。
- W03 玩家身份与当前任务动机：玩家是候补队指挥官；带一支新募小队打满 8 轮轮换赛——用招募、合成与哨卫羁绊把仓促成军的队伍磨成正式编制。
- W04 失败代价与结局表达：候补队被淘汰=编制解散、候补徽章收回（C03 失败意象）；8 轮出线=正式编制授旗、航道防线交接（C03 胜利意象）。
- W05 叙事来源：六种单位=星港口岸的候补编制（巡逻兵/装甲哨/狙击手/医疗无人机/破甲者/侦察蜂均为原创造型的星务机兵与无人机）；哨卫羁绊=同排并肩操典；对手脚本=轮换赛既定对阵表。全部原创，不用商业作品命名。
- W06 视觉风格与色彩材质：星港工业风；主色＝星港钛 #8A97A8、航道蓝 #2C4A6E、能量青 #3ED3C2、警报橙 #E4762C；材质为舷窗玻璃、防滑甲板、金属机兵涂装。

## 10. 过场视频 [C01–C03]

- C01 轮换赛开幕（Opening，8 秒，1280×720@24fps）
  - 触发时机：首次由标题进入对局（第 1 轮准备期）之前，每局一次
  - 内容与角色场景：星港灯泊港全景——候补甲板灯火亮起、看台广播响起、各防区小队旗逐一升起，指挥官把候补徽章按上指挥台
  - 资产对应：单位与甲板与游戏内模型同源
  - 可跳过：Esc/Enter 跳过 → 直接进入第 1 轮准备期；自然播完 → 进入第 1 轮准备期
  - 状态一致：跳过与自然播完后初始状态一致；播放期间不推进任何游戏计时；重开后开场 CG 可再次跳过
- C02 首次合成（Event，5 秒，1280×720@24fps）
  - 触发时机：每局首次三合一合成成立时，每局一次
  - 内容与角色场景：三名同型机兵走入光柱合而为一、星级徽章点亮、全队敬礼——候补小队第一次成军时刻
  - 资产对应：合成单位与游戏内模型同源
  - 可跳过：Esc/Enter 跳过 → 直接继续准备期操作；自然播完 → 继续准备期
  - 状态一致：播放期间不推进准备期倒计时与任何游戏计时
- C03 出线或解散（Ending，8 秒，1280×720@24fps，双意象共用条目）
  - 触发时机：V01/V02 成立、终局结算面板出现之前，每局一次
  - 内容与角色场景：胜利意象=正式编制授旗、航道防线舷窗亮起；失败意象=候补徽章收回、甲板灯火渐暗
  - 资产对应：单位与甲板与游戏内模型同源
  - 可跳过：Esc/Enter 跳过 → 直接进入对应结算面板；自然播完 → 进入对应结算面板
  - 状态一致：仅在真实 V01/V02 后触发；播放期间不推进任何游戏计时

## 生成任务明确性补充（2026-10-12）

> 本补充只约束游戏生成输入，不引用 rubric。所有生成器必须以本文件规则和下列 JSONL 任务为准；未列出的装饰细节可以自由发挥，但不得省略已列资产或生命周期。

### 故事与流程最低合同
- **玩家身份与当前冲突**：以 §1、§8 的角色/世界/冲突为唯一叙事入口；开局必须让玩家知道“我是谁、现在要解决什么问题”。
- **阶段性目标**：必须有可操作的阶段目标、至少一次状态变化/升级，并在 §7 的胜利、失败、重开入口中闭环；不能只生成一个无结果的场景演示。
- **结果承接**：胜利/失败都要有明确结果文案或演出，并回到可重开、暂停或标题入口；视频、音频和 VFX 不得推进未完成的玩法状态。

### 生成任务清单（JSONL 冻结口径）
- scene：1 个；必须生成连贯可游玩的空间，不得出现下半部文字、拼贴面板、物体 lineup 或 UI。
- object：6 个（text-to-3D 4，image-to-3D 2）；object 任务资产为：patrol_soldier, armored_sentry, sniper, armor_breaker, medic_drone, scout_bee。每项只允许一个物体；组合物必须拆成独立任务。
- motion：20 个；覆盖动作：idle, walk, attack, hit_react, death, idle, walk, attack, hit_react, death, idle, walk, attack, hit_react, death, idle, walk, attack, hit_react, death。
- video/audio/mechanic/UI：分别为 3/18/1/1 个任务；若某项为 0，只能是本案例明确的 N/A，不得默默遗漏。

### Video / motion / audio 生命周期
- Video 每项必须写清 `trigger`、`start_condition`、`duration_sec`、`skippable`、`skip_behavior`、`end_condition` 和进入的下一个游戏状态；播放期间不得偷偷消耗计时或改变战斗/任务数值。
- Motion 每项必须写清 `source_asset`、`trigger`、`start_condition`、`duration_sec`、`loop`、`end_condition` 和 `cancel_behavior`；动作要与对应输入/机制事件绑定，不可只写“walk animation”。
- Audio 每项必须写清触发事件、时长、`loop`、`stop_condition`、优先级和 ducking；关键命中/提示音必须与事件帧同步，暂停/结算时按 §9 处理。

### Mechanic / UI / 游玩手感
- Mechanic JSON 与 §1–§7 配对：每个输入都要有 precondition、state_change、feedback、next_state；必须说明失败/禁用分支。
- UI JSON 与 §9/F10 配对：HUD、菜单、结算、暂停、错误/禁用态要有 state binding；关键状态不能只用颜色表达。
- 手感冻结：相机跟随/构图、FOV、碰撞/遮挡、镜头调整与镜头震动必须在 §9 说明；震动反馈必须写明触发、强度和持续时间，并提供关闭设置且不改变判定。

### VFX 时机合同
每个特效必须写清 `trigger event`、预备/前摇、active window、持续时间、结束条件、被打断/取消条件，以及和相机震动、音效、UI 的同步关系；命中特效、失败特效、胜利特效不能只写“有粒子”。
