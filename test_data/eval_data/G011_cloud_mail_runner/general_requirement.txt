## 1. 定位与完整流程 [S01–S05]

- S01 类型：2.5D 侧视自动前进跑酷，单人单局，有限路段（500 米）。本测例包含的能力：跳跃/滑铲过障、上层高收益与下层稳妥双路线、收集与唯一 ID 去重、碰撞-检查点复位、终点结算、开场/路线/结算视频、跑酷手感演出层。
- S02 核心循环一句话：自动前进 → 跳跃/滑铲过障 → 双路线取舍收集 → 抵达终点结算。
- S03 流程：开始界面 → 进入邮路（首次进入前播 C01）→ 500 米有限路段（可选上层 3m 通道）→ 抵达终点 → 结算（收集、距离、碰撞、总分；面板前播 C03）→ 重开或返回。
- S04 最低完整流程：开始界面、可操作奔跑、结算界面、重开必须全部存在且有真实入口。
- S05 失败恢复入口：碰撞后自动回最近检查点继续（1 秒无敌只抑制重复受击）；第 4 次碰撞判负；结算界面一键重开；游玩中 Esc 暂停。

## 2. 完整核心循环与阶段 [S06–S10]

- S06 启动与标题
  - input：系统启动加载完成（触发方：系统）；玩家按 Enter/点击「开始」
  - precondition：构建可启动且资源加载完成
  - state_change：进入「标题」状态；首次开始时按 §10 C01 触发开场视频
  - feedback：标题界面按 §9 F10 呈现
  - next_actions：进入「邮路奔跑」
  - outcome：无跨局状态写入
- S07 邮路奔跑
  - input：Space/W/↑＝跳跃、S/↓＝滑铲、Esc＝暂停（触发方：玩家）；自动前进与路段内容由 seed 驱动（触发方：系统）
  - precondition：处于奔跑状态且非暂停/结算/视频
  - state_change：按 §6 M01–M05 结算每次输入；距离、收集集合、碰撞计数、检查点实时更新
  - feedback：按 §9 F05（跳跃/滑铲轨迹、收集火花、碰撞闪白与复位、检查点灯标）
  - next_actions：抵达 500 米 →「胜利结算」；第 4 次碰撞 →「失败结算」
  - outcome：按 §7 V01/V02 判定，同帧裁决按 G06
- S08 胜利结算
  - input：Enter=重开 / Esc=返回（触发方：玩家）
  - precondition：V01 成立（抵达终点）
  - state_change：进入「胜利结算」；面板出现前按 §10 C03 播放结算视频（每局一次）
  - feedback：结算面板显示收集数、完赛距离、碰撞次数、总分（G03 公式）
  - next_actions：重开（全量重置）或返回标题
  - outcome：无跨局状态写入
- S09 失败结算
  - input：Enter=重开 / Esc=返回（触发方：玩家）
  - precondition：V02 成立（第 4 次碰撞，注明碰撞超限）
  - state_change：进入「失败结算」；面板出现前按 §10 C03 播放结算视频的失败意象（每局一次）
  - feedback：失败面板注明「碰撞超限」
  - next_actions：重开本局
  - outcome：全量重置
- S10 暂停
  - input：Esc（触发方：玩家）；窗口失焦自动触发（触发方：系统）
  - precondition：处于奔跑状态
  - state_change：暂停覆盖层打开，前进、计时与输入冻结
  - feedback：暂停面板（继续/重开/返回/设置）
  - next_actions：Esc 或「继续」→ 回到奔跑
  - outcome：恢复后状态与暂停前逐字段一致

## 3. 数值口径与全局规则 [G01–G06]

- G01 统一刻度：距离单位为米；总分与计数为整数；时间采用游戏模拟秒（暂停冻结）；距离取最大已到达进度向下取整并钳制 0–500（结算距离口径）。
- G02 移动参数：角色自动前进 8 米/秒；跳跃历时 0.9 秒、峰值高度 2.2 米（可越过 1.6 米以下高障）；滑铲历时 0.7 秒、通过高度 1.0 米（可穿过 1.2 米以上低障）；跳跃与滑铲在动作结束前不可打断，落地/起身后方可接下一动作。
- G03 结算公式：总分 = 收集光件数 × 50 ＋ 完赛距离（米）× 2 − 碰撞次数 × 100。独立 oracle 数例：满收集（40）零碰撞完赛 = 40×50+500×2 = **3000**；32 收集、1 碰撞完赛 = 32×50+500×2−100 = **2500**。
- G04 障碍布局（zkx 裁决冻结）：连续障组按「高-低-高」实例化，中心间距 **9 米**，沿跑向碰撞宽 0.8 米（原 2.2 米间距短于 0.9 秒不可打断跳跃的实际位移，予以废止）；三类障碍共 20 处（高障 8、低障 8、连续障 4 组×3 个）；上层通道为高度 3 米的平台段，入口必须设 1.5 米中继台阶（每次垂直上升 ≤2.2 米）；前 50 米为无障碍教学段（仅光件）；冻结布局须提供至少一条有效输入轨迹。
- G05 固定种子复现：路段拼接序列由 fixed_seed=1011 唯一确定；同版本构建、同 seed 下两次完整跑动，路段障碍/收集/检查点序列逐项 diff=0；玩家操作差异只改变角色轨迹，不改变路段内容。
- G06 碰撞、检查点与同帧裁决：碰撞上限 3 次（第 4 次碰撞判负）；检查点每 100 米一个（0/100/200/300/400 米，共 5 个）；碰撞后角色回最近已越过的检查点并获得 1 模拟秒无敌（只抑制重复受击，不重置碰撞计数），碰撞计数保留；碰撞复位不撤销已拾取的收集、不重复计分。同帧裁决：抵达终点与第 4 次碰撞同帧 → 判负优先（先失败后成功）。Esc 暂停冻结前进、计时与输入。

## 4. 操作与输入 [I01–I07]

- I01 键位：Space 或 W/↑＝跳跃；S/↓＝滑铲；Esc＝暂停/继续；结算界面 Enter＝重开。
- I02 输入语义边界：动作未结束时重复按键不产生叠加（无二段跳、无连滑）；暂停/结算/视频期间玩法键无效；被拒绝输入不产生任何状态变化。
- I03 键盘为完整输入方式；菜单可仅用键盘操作。
- I04 输入优先级：暂停与结算状态阻断全部玩法输入；同帧互斥动作按 I01 列举顺序取首个。
- I05 焦点与失焦：点击画布捕获输入焦点；窗口失焦自动暂停。
- I06 UI 必显状态：距离（米）、收集数、碰撞计数（0–3）、当前检查点编号、总分实时值。
- I07 输入延迟目标：按键到画面反馈 ≤100 毫秒（P95，≥30 次采样/类别）。

## 6. 机制系统 [M01–M05]

- M01 三类障碍应对（主机制）
  - input：跳跃/滑铲键（触发方：玩家）
  - precondition：处于奔跑状态且非暂停/结算/视频；当前无未完成的跳跃/滑铲动作
  - state_change：高障（1.6 米级）需跳跃越过；低障（1.2 米以上横杆）需滑铲穿过；连续障（高-低-高、中心间距 9 米）需「跳-铲-跳」节奏链；应对错误 → 碰撞（M04）
  - observable：碰撞事件（含障碍类型与坐标）、按键时序流水、过障成功事件
  - invalid_case：动作未结束时重复按键不叠加；暂停/结算期间输入被拒绝且无副作用
  - recovery：碰撞走 M04 复位；结算界面重开为最终出路
- M02 收集物与结算
  - input：路线接触光件（触发方：系统）
  - precondition：处于奔跑状态；该光件唯一 ID 尚未进入本局收集集合
  - state_change：接触即收集，唯一 ID 计入集合、计数 +1；碰撞复位不撤销已拾取物、不重复计分；终点按 G03 公式结算（距离按 G01 取整口径）
  - observable：collect 事件（含唯一 ID 与坐标）与结算对账（总分=逐项加权和，容差 0）
  - invalid_case：已收集 ID 再次接触不重复计分
  - recovery：重开后收集集合清空
- M03 固定种子复现
  - input：seed=1011（局开始）（触发方：系统）
  - precondition：新局开始
  - state_change：路段拼接序列确定化（障碍/收集/检查点布局）
  - observable：同 seed 双跑路段序列 diff=0
  - invalid_case：运行中不得重排路段内容
  - recovery：重开回同 seed 初始状态
- M04 碰撞与检查点复位
  - input：错误应对撞上障碍（触发方：系统）
  - precondition：处于奔跑状态
  - state_change：碰撞计数 +1 → 角色回最近已越过检查点并获得 1 模拟秒无敌（只抑制重复受击、不重置碰撞计数、不撤销已拾取收集）；碰撞计数达 4 → 判负结算
  - observable：crash 事件（计数与检查点 ID）、checkpoint 事件
  - invalid_case：无敌期内接触障碍不再累计碰撞
  - recovery：复位后继续奔跑；判负走 V02
- M05 胜负与重开
  - input：抵达 500 米终点 / 第 4 次碰撞 / 结算界面（触发方：系统判定/玩家）
  - precondition：处于奔跑状态或结算状态
  - state_change：抵终点 → 胜利结算；第 4 次碰撞 → 失败结算（注明原因）；结算后奔跑冻结；同帧裁决按 G06（判负优先）
  - observable：finish / lose 事件与结算面板
  - invalid_case：结算后再触发判定被拒绝（每局一次）
  - recovery：重开=全量重置（距离/收集/碰撞/路段按 seed 复现）

## 7. 成功、失败与恢复 [V01–V06]

- V01 成功条件：抵达 500 米终点 → 结算（收集数、完赛距离、碰撞数、总分）。
- V02 失败条件：第 4 次碰撞 → 判负结算（注明「碰撞超限」）；与终点同帧按 G06 判负优先。
- V03 恢复语义：单次碰撞回最近检查点继续（碰撞计数保留、收集保留）；判负/结算后一键重开；重开后路段序列、收集、碰撞全量按 seed 重置。
- V04 persistent_state：无（重开全量清空；最好成绩可作展示但不作为验收需求、不要求跨会话保存）。
- V05 persistent_state 生命周期：动作级即时结算；局内状态（距离/收集/碰撞）局内保留、重开清空；无跨局保留。
- V06 软锁与不可达处理：不设永久软锁——冻结布局保证至少一条有效输入轨迹；判定不可达时按 V02 失败语义结算而非无限等待；结算界面重开为最终恢复出路。

## 8. 世界设定与创作基线 [W01–W08]

- W01 世界与时代背景：云端邮路的最后一班信——暴风云带正在吞没这条悬于天际的邮路，这是云邮时代结束前的最后一次投递。
- W02 场景所在地：500 米悬空邮路，云海在其下翻涌；上层 3 米高的暴风脊线通道（高收集密度）与下层云面稳妥栈道并行，尽头是云端灯塔。
- W03 玩家身份与当前任务动机：玩家是最后一位云端邮差，背着最后一批急件；动机是在邮路被暴风吞没前，把每一件光件（邮路信标）安全送到灯塔。
- W04 失败代价与结局表达：失败=第四次碰撞后急件散落云海（C03 失败意象）；胜利=灯塔点亮、送达完成（C03 胜利意象）。
- W05 叙事来源：光件=邮路信标件（收集目标）；高障/低障/连续障=暴风卷起的云岩与断裂横梁；检查点=沿途补给灯站；上层通道=邮路的暴风脊线（高风险高收益）。全部原创，不使用商业作品命名或造型。
- W06 视觉风格与色彩材质：明快手绘感的云海世界；主色=云白 #EAF2F8、信件金 #E8C559、暴风灰蓝 #6E8FA3、灯塔橙 #E4762C、光件青 #7FD8E8；材质为云岩、木质栈道、帆布邮包。
- W07 环境氛围与声音语言：风声与云层低鸣为底；音效语言为「跳跃风切+滑铲摩擦+收集叮响+碰撞闷响+灯塔钟声」，全部音效按 §9 F06 冻结清单交付。
- W08 故事表达方式：开场视频（C01）交代最后班信与灯塔目标 → 路线视频（C02）承载上下层取舍的过程叙事 → 结算视频（C03）收束；叙事提示不阻断控制、不改变数值；提前失败允许直接进入失败结局。

## 9. 演出、镜头与反馈 [F01–F10]

- F01 视角与镜头：2.5D 侧视跟随相机；前视安全区 ≥ 屏宽 35%（后方 ≥10%）；跳跃/滑铲不改变 FOV；镜头仅短促 0.06 秒轻微抖动（碰撞）；镜头重置仅在明确切场/复位时。
- F02 关键操作镜头变化：碰撞 0.06s 轻微抖动（幅度 ≤ 画面高度 1.5%）；收集不震屏；胜利镜头缓推灯塔。设置提供「镜头震动开/关」与「减少动态效果」（关闭抖动与剧烈旋转、保留状态提示；关闭不影响判定与数值）。
- F03 输入与延迟：见 I07（≤100ms P95）；顿帧不改变计时口径。
- F04 环境常驻效果：云海流动、远方云柱、检查点灯标呼吸光。纯表现层，不参与判定。
- F05 事件反馈表（事件 → 画面表现 → 音效 → 结束条件，全部冻结需求）：

| 事件 | 画面表现 | 音效 | 结束条件 |
|---|---|---|---|
| 跳跃起跳 | 起跳尘土＋跳跃轨迹残影（jump_trail） | 跳跃风切音 | 0.9 秒动作结束 |
| 滑铲 | 滑铲尘土（slide_dust） | 滑铲摩擦音 | 0.7 秒动作结束 |

## 生成任务明确性补充（2026-10-12）

> 本补充只约束游戏生成输入，不引用 rubric。所有生成器必须以本文件规则和下列 JSONL 任务为准；未列出的装饰细节可以自由发挥，但不得省略已列资产或生命周期。

### 故事与流程最低合同
- **玩家身份与当前冲突**：以 §1、§8 的角色/世界/冲突为唯一叙事入口；开局必须让玩家知道“我是谁、现在要解决什么问题”。
- **阶段性目标**：必须有可操作的阶段目标、至少一次状态变化/升级，并在 §7 的胜利、失败、重开入口中闭环；不能只生成一个无结果的场景演示。
- **结果承接**：胜利/失败都要有明确结果文案或演出，并回到可重开、暂停或标题入口；视频、音频和 VFX 不得推进未完成的玩法状态。

### 生成任务清单（JSONL 冻结口径）
- scene：1 个；必须生成连贯可游玩的空间，不得出现下半部文字、拼贴面板、物体 lineup 或 UI。
- object：7 个（text-to-3D 5，image-to-3D 2）；object 任务资产为：mail_courier, high_barrier, low_barrier_rail, relay_step, light_pickup, checkpoint_beacon_post, finish_lighthouse_gate。每项只允许一个物体；组合物必须拆成独立任务。
- motion：4 个；覆盖动作：run, jump, slide, crash_recover。
- video/audio/mechanic/UI：分别为 3/8/1/1 个任务；若某项为 0，只能是本案例明确的 N/A，不得默默遗漏。

### Video / motion / audio 生命周期
- Video 每项必须写清 `trigger`、`start_condition`、`duration_sec`、`skippable`、`skip_behavior`、`end_condition` 和进入的下一个游戏状态；播放期间不得偷偷消耗计时或改变战斗/任务数值。
- Motion 每项必须写清 `source_asset`、`trigger`、`start_condition`、`duration_sec`、`loop`、`end_condition` 和 `cancel_behavior`；动作要与对应输入/机制事件绑定，不可只写“walk animation”。
- Audio 每项必须写清触发事件、时长、`loop`、`stop_condition`、优先级和 ducking；关键命中/提示音必须与事件帧同步，暂停/结算时按 §9 处理。

### Mechanic / UI / 游玩手感
- Mechanic JSON 与 §1–§7 配对：每个输入都要有 precondition、state_change、feedback、next_state；必须说明失败/禁用分支。
- UI JSON 与 §9/F10 配对：HUD、菜单、结算、暂停、错误/禁用态要有 state binding；关键状态不能只用颜色表达。
- 手感冻结：相机跟随/构图、FOV、碰撞/遮挡、镜头调整与镜头震动必须在 §9 说明；震动反馈必须写明触发、强度和持续时间，并提供关闭设置且不改变判定。

### VFX 时机合同
每个特效必须写清 `trigger event`、预备/前摇、active window、持续时间、结束条件、被打断/取消条件，以及和相机震动、音效、UI 的同步关系；命中特效、失败特效、胜利特效不能只写“有粒子”。
