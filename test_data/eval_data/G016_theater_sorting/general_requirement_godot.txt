## 0. 标题、版本与使用说明

- 作品名：《仓储机器人整理旧剧院》；版本：mechanics-v3（2026-10-11 完整性修订：补世界设定、镜头/输入、演出反馈、视频与正向范围清单）；运行引擎：**Godot 4.x（Windows 桌面构建）**（本 spec、rubric 与 asset 任务 JSONL 中的 mechanic/ui/pipeline 任务引擎字段保持一致，引擎唯一冻结）；输入方式：键盘。
- 原创边界：推箱子的公有领域规则机制可复用；本作全部名称、角色、场景、文案与美术必须原创，不使用任何商业作品的关卡集、角色、徽记、造型或台词。
- 规则优先级：本文件全局数值与规则 ＞ 机制章节 ＞ 关卡实例 ＞ 生成器自由补充；未指定数值可作为明确标注的配置默认值，不得伪装成本文既定要求。
- 本文件用于游戏生成模型，目标是输出可操作的俯视格子推箱解谜游戏；文档存在不等于玩法完成，静态页面、类名或演示视频不能单独证明可玩。任何任务关键目标不得因随机失败被永久删除（本题无随机玩法内容）。

## 1. 定位与完整流程 [S01–S05]

- S01 类型：2D 俯视格子推箱解谜，单人单屏。本测例包含的能力：三关静态棋盘、推动与覆盖检测、撤销与重置、死角提示、步数预算、开场与结算视频、舞台主题表现层。
- S02 核心循环一句话：观察布局 → 规划推动序 → 执行 → 目标覆盖检测 → 过关或重置。
- S03 流程：标题界面 → 关卡选择（3 关全开，无解锁门槛）→ 游玩 → 过关结算（步数、撤销次数）→ 下一关或重开；任意界面可返回标题。
- S04 最低完整流程：标题、选关、游玩、过关结算、失败提示、重置、重开必须全部存在且有真实入口。
- S05 失败恢复入口：游玩中任意时刻可撤销（Z）或整关重置（R）；失败结算界面提供「重试本关」。

## 2. 完整核心循环与阶段 [S06–S11]

完整循环：启动与标题 → 关卡选择 → 游玩 → 过关结算 → 下一关或重开 → 返回标题/重试。每阶段六要素如下（引用本 spec §3–§7 与 §9 对应规则）：

- S06 启动与标题
  - input：系统启动加载完成（触发方：系统）；玩家按 Enter/点击「开始」
  - precondition：构建可启动且资源加载完成（rubric D3 断言）
  - state_change：游戏进入「标题」状态；首次进入时按 §10 C01 触发开场视频
  - feedback：标题界面按 §9 F10 呈现（开始/退出按钮、引擎版本号）
  - next_actions：进入「关卡选择」
  - outcome：无跨局状态写入（见 §8 V04）
- S07 关卡选择
  - input：方向键＋Enter（触发方：玩家）
  - precondition：标题或结算界面已提供选关入口
  - state_change：进入「关卡选择」状态，三关全部可选
  - feedback：关卡卡片显示本关历史完成标记（局内，仅本会话）
  - next_actions：载入所选关 →「游玩」
  - outcome：按 §6 M06 载入静态布局，全部状态按该关初始值
- S08 游玩
  - input：方向键/WASD 移动、Z 撤销、R 重置、Esc 暂停（触发方：玩家）
  - precondition：关卡载入完成且非暂停/结算状态
  - state_change：按 §6 M01–M05 结算每次输入；步数、覆盖计数、undo_count 实时更新
  - feedback：按 §9 F05/F06 呈现推动、覆盖、非法、撤销、重置反馈
  - next_actions：覆盖计数==目标点数 →「过关结算」；步数耗尽 →「失败结算」
  - outcome：按 §8 V01/V02 判定，优先级按 §3 G07
- S09 过关结算
  - input：Enter＝下一关 / R＝重开本关 / Esc＝返回选关（触发方：玩家）
  - precondition：V01 成立（覆盖计数==目标点数）
  - state_change：进入「过关结算」状态；棋盘冻结；第三关完成时按 §10 C02 触发结算视频
  - feedback：结算面板显示步数、undo_count、用时
  - next_actions：下一关（未过完）/ 总结算（三关完成）/ 重开
  - outcome：不写入跨局状态（见 §8 V04）
- S10 失败结算
  - input：Enter＝重试本关 / Esc＝返回选关（触发方：玩家）
  - precondition：V02 成立（步数预算耗尽且未达成覆盖）
  - state_change：进入「失败结算」状态；棋盘冻结
  - feedback：失败面板注明原因「步数预算耗尽」并给重试入口
  - next_actions：重试本关（全量按初始布局重载）
  - outcome：本关状态清空，无跨局副作用
- S11 暂停
  - input：Esc（触发方：玩家）
  - precondition：处于游玩状态
  - state_change：暂停覆盖层打开，输入与棋盘逻辑冻结
  - feedback：暂停面板（继续/重置本关/返回选关/设置）
  - next_actions：Esc 或「继续」→ 回到游玩
  - outcome：恢复后状态与暂停前逐格一致（§3 G05）

## 3. 数值口径与全局规则 [G01–G07]

- G01 统一刻度：棋盘为格子坐标（列,行），原点 (0,0) 位于左上；格子类型＝墙 / 地面 / 目标点；状态变量＝玩家坐标、每箱坐标、覆盖计数（箱子位于目标点的数量）、已用步数、undo_count。目标点以「金色圆环＋『目标』文字标签」标识（不只靠颜色，见 F10）。
- G02 步数预算：L1=40 步、L2=60 步、L3=90 步；每次有效移动或有效推箱计 1 步；被拒绝的输入、撤销、重置、菜单导航不计步。
- G03 难度：单档「标准」；不提供难度选择。
- G04 随机种子：fixed_seed=1016。三关布局为静态数据，不含随机生成；本 seed 仅用于保证同版本构建内任何内部随机流（如表现层粒子）不影响棋盘规则结果。
- G05 暂停与模拟时间：Esc 暂停冻结输入与棋盘逻辑；暂停、结算、菜单、视频播放期间不推进任何游戏状态；UI 过渡不得触发格子逻辑；窗口失焦自动暂停。
- G06 状态转移 oracle（独立可复核）：给定初始棋盘与输入序列，最终棋盘唯一确定。数例：局部棋局中玩家位于 (2,1)、箱子位于 (2,2)、(2,3) 为目标点、其右为空地；输入 [右] 后必然产生事件流 `move(player,2,1→2,2)`、`push(box,2,2→2,3)`、`cover(2,3)=true`、`steps+1`，玩家位于 (2,2)、箱子位于 (2,3)、覆盖计数 +1；任何偏离即 FAIL。
- G07 优先级与统计（本包冻结值）：同一有效步使「覆盖计数==目标点数」与「步数预算恰好耗尽」同时成立时，判胜优先于判负（先完成目标）。undo_count＝本关成功撤销的有效步总数；被拒输入不计入 undo_count；撤销本身不消耗步数、不增加步数；过关结算必须同时显示已用步数与 undo_count。

## 4. 操作与输入 [I01–I07]

- I01 键位：方向键或 WASD＝移动一格（面向相邻箱子则推动）；Z＝撤销一步；R＝整关重置（带确认）；Esc＝暂停/关闭面板；Enter＝确认。
- I02 输入语义边界：面向墙移动、推动被墙/另一箱阻挡的箱子、忙时与面板打开时的玩法键，一律拒绝且不消耗步数、不产生状态变化；被拒绝输入不得被记为一步、不得计入 undo_count。
- I03 键盘为完整输入方式；菜单可仅用键盘操作。
- I04 输入优先级：暂停与结算状态阻断全部玩法输入；面板打开时玩法键不串入；同帧多输入按 §6 各机制声明的顺序结算（先 movement、后 undo、后 reset）。
- I05 焦点与失焦规则：点击画布捕获输入焦点；面板层阻断点击穿透；窗口失焦自动暂停（不依赖 G06）。
- I06 UI 必须显示的状态：本关号、步数预算剩余/已用、覆盖计数/目标点数、undo_count；HUD 对照见 rubric。
- I07 输入延迟目标：按键到对应画面反馈（移动动画或拒绝反馈）≤ 100 毫秒（WebGL/HTML5 环境目标 ≤ 150 毫秒）；延迟异常须在设置中可见当前帧率。

## 6. 机制系统 [M01–M06]

- M01 推动限制（主机制）
  - input：移动键（方向键/WASD）
  - precondition：处于游玩状态（非暂停/结算/面板）；目标格在棋盘界内
  - state_change：目标格为空地面或目标点 → 玩家移入一格；目标格为箱子且箱子落点格（同方向再前进一格）为空地面或目标点 → 玩家与箱子各前进一格；箱子只能推不能拉；目标格为墙、或箱子落点为墙/另一箱 → 整体拒绝且无副作用
  - observable：每步产生棋盘快照与事件 `move` / `push` / `reject`（含方向与坐标）；有效步 steps+1；被拒事件不伴随 steps+1
  - invalid_case：面向墙、推箱顶墙、推箱顶第二箱 → reject，坐标不变、步数不变
  - recovery：Z 撤销最近一次有效步（见 M02）或 R 整关重置
- M02 撤销栈（事务性回滚）
  - input：Z
  - precondition：存在至少一次未回滚的有效步；处于游玩状态
  - state_change：回退最近一次有效步——玩家坐标、全部箱坐标、覆盖计数、步数在同一事务内同步回滚；undo_count+1；可连续回溯到本关开局；开局（无可回滚步）时 Z 无效且不计数
  - observable：`undo` 事件与回滚后棋盘快照；回滚后状态与所撤销步骤执行前逐格一致（diff=0）
  - invalid_case：无可回滚步时 Z → 无事件副作用、undo_count 不变
  - recovery：撤销链到开局即止；R 重置可随时使用
- M03 死角判定与提示
  - input：系统在每次 push 后判定
  - precondition：刚发生一次有效 `push`
  - state_change：箱子被推入「贴墙角格」（其行进正交两侧均为墙/界的格子）且该格不是目标点时，标记该箱为不可解；不强制失败，玩家可撤销或重置
  - observable：`deadlock` 事件（含箱子坐标）与画面提示（该箱红色高亮＋「该箱已卡死角」文字提示一次）
  - invalid_case：箱子落入目标点角格不触发 deadlock；普通贴墙（单侧）不误报
  - recovery：Z 撤销该步即可解除标记
- M04 目标覆盖检测
  - input：每次 push 后系统检测
  - precondition：发生过一次有效 `push`（或撤销恢复）
  - state_change：覆盖计数＝位于目标点的箱子数；计数==目标点数 → 过关结算（优先级按 G07）
  - observable：`cover`/`uncover` 事件、HUD 覆盖计数、`win` 事件
  - invalid_case：部分覆盖不判胜；箱子被推离目标点产生 `uncover`
  - recovery：无失败态；覆盖后棋盘冻结
- M05 守护机器人（玩家角色）移动
  - input：移动键
  - precondition：与 M01 同一判定入口
  - state_change：一格一格移动，不可穿墙、不可穿越箱子；移动逻辑与 M01 同一判定
  - observable：移动事件与坐标流水
  - invalid_case：越界/穿墙/穿箱输入拒绝
  - recovery：同 M01
- M06 关卡切换
  - input：过关结算界面（下一关）/ 选关界面
  - precondition：V01 成立或玩家主动从选关进入
  - state_change：载入对应静态布局，玩家/箱子/步数/覆盖计数/undo_count 全部按该关初始值重置
  - observable：`level_loaded` 事件与关卡号显示
  - invalid_case：非法关卡号请求拒绝
  - recovery：载入失败重试或返回标题

## 7. 成功、失败与恢复 [V01–V05]

- V01 成功条件：本关全部目标点被箱子覆盖（覆盖计数==目标点数）→ 过关结算，显示已用步数与 undo_count。
- V02 失败条件：步数预算耗尽且未达成覆盖 → 失败结算（区别于主动重置）；无 HP、无时限；与覆盖同时达成时按 G07 判胜。
- V03 恢复语义：Z 撤销可回溯到开局（M02）；R 整关重置回到本关初始布局（含 undo_count 清零）；失败结算后可重试本关；一切恢复不需要读档。
- V04 persistent_state：无（重开全量清空；无跨关解锁、无收集品、无跨关状态）。
- V05 persistent_state 生命周期：当前动作级状态即时结算；当前局级状态（步数/覆盖/undo_count）局内保留、重开清空；无跨局保留状态。
- V06 软锁与不可达处理：不设永久软锁——死角仅提示不判负，关键目标均可通过正常操作或 R 重置达成；判定不可达时按 V02 失败语义结算而非无限等待。

## 8. 世界设定与创作基线 [W01–W08]

- W01 世界与时代背景：近未来的小城「暮椿镇」，废弃三十年的老剧院「暮椿剧院」将在明晚重新开幕；镇上唯一能在一夜之间完成整备的，是剧院遗留的仓储整理机器人。
- W02 场景所在地：暮椿剧院内部——关卡一为主舞台区（幕布与追光）、关卡二为后台仓储区（道具架与缆绳）、关卡三为观众厅（座椅与包厢）。
- W03 玩家身份与当前任务：玩家操作整理机器人「初幕」；当前任务：在天亮前把全部道具箱推回舞台标记位，让开幕灯光测试可以照常进行。
- W04 失败代价与结局表达：失败＝天亮前来不及完成整备（步数预算耗尽），开幕被迫推迟；结局表达见 §10 C02——三关完成时剧院重新亮灯，开幕如期举行。
- W05 叙事来源：道具箱＝剧院历次演出遗留的布景箱（因此数量随区域递增）；目标点＝舞台灯光师用金色标记贴出的存放位；机器人「初幕」＝剧院老机械师退休前留下的整理机。所有角色与物件均原创，不使用任何商业剧院/机器人作品的命名或造型。
- W06 视觉风格与色彩材质：2D 手绘风格化俯视画面；主色＝暖木色（#C89B6D 系）＋舞台深红（#8E2F3C 系）＋目标金（#F2C14E）；材质以哑光木材、绒面幕布、磨损金属为主；三关通过主题色变体区分（舞台偏红金、后台偏灰木、观众厅偏蓝绒）。
- W07 环境氛围与声音语言：安静夜间的剧院——常驻低鸣环境声、尘埃光束（F04）；音效语言为「木质滑动声＋机械伺服声＋灯光提示音」，全部音效按 §9 F06 冻结清单交付。
- W08 故事表达方式：开场视频（C01）交代任务 → 关卡主题变体承载过程叙事 → 结算视频（C02）与结算面板收束；故事只做包装与节奏，不改变任何机制数值。

## 9. 演出、镜头与反馈 [F01–F10]

- F01 视角与镜头：固定正交俯视（90°），整张棋盘在默认窗口（1280×720）内全部可见，无跟随、无平移；镜头边界＝棋盘外接矩形外加 8% 余量。
- F02 关键操作镜头变化：过关瞬间镜头向该关最后一个被覆盖目标点轻微推近 5%（2 秒内完成并保持到结算）；失败时镜头轻微下沉变暗 0.5 秒；无震动类镜头变化。
- F03 输入与延迟：见 I07；Z/R 的反馈延迟同 I07 目标。
- F04 环境常驻效果：舞台区追光光束＋浮尘粒子（低密度，不遮挡格线）；后台区吊缆微摆；观众厅座椅尘埃。常驻效果纯表现层，不参与判定。
- F05 事件反馈表（事件 → 表现 → 结束条件，全部为冻结需求）：

| 事件 | 画面表现 | 音效 | 结束条件 |
|---|---|---|---|
| 推动成功 | 箱体滑动 0.15s＋箱底尘土小粒子 | 木质滑动声（与动画同步起止） | 滑动到位即停 |
| 目标覆盖 | 目标点金圈点亮 0.3s＋箱子描金边 | 「叮」确认音 | 覆盖状态常亮至变化 |
| 非法移动 | 机器人原地抖动 0.3s＋目标格红框闪 1 次 | 短促否定音 | 0.3s 结束 |
| 撤销 | 箱体与机器人反向回放 0.15s | 回摆音（滑动声倒放感） | 回放到位即停 |
| 重置确认 | 幕布暗转 0.5s | 幕布摩擦声 | 布局重载完成 |
| 过关 | 全场景灯组亮起＋彩带粒子 | 上扬提示音＋掌声（一次，不循环） | 进入结算即淡出 |
| 失败 | 灯光转暗＋HUD 变灰 | 低沉提示音 | 进入失败面板即停 |
| 死角提示 | 该箱红色高亮＋文字标签一次 | 警示音一次 | 提示 2s 后仅保留描边 |

- F06 关键音效清单：木质滑动、确认「叮」、否定音、回摆音、幕布声、胜利音、掌声、失败音、警示音；环境音：剧院低鸣（常驻循环，暂停时静音）；循环音开始/结束：环境低鸣随关卡载入开始、随结算/返回标题淡出 0.5s；无配音需求（对白以文本呈现）。
- F07 VFX 信息性与遮挡约束：目标点金色圆环与死角红色高亮承担玩法信息（可辨认可解状态）；尘土与彩带粒子只出现在格间空隙，单帧粒子数 ≤ 40，不得遮挡格线与 HUD。
- F08 音画同步：滑动/回放音与对应动画同帧起止；覆盖确认音在 cover 事件帧触发；胜利音在 win 事件帧触发。
- F09 屏幕震动：仅过关瞬间 0.2 秒小幅震动；设置界面提供「镜头震动开/关」（关闭不影响判定）。
- F10 前端界面：标题（开始/设置/退出）→ 选关（三关卡片＋完成标记）→ HUD（关卡号、步数预算剩余/已用、覆盖计数/目标点数、undo_count）→ 过关结算（步数/undo_count/用时/下一关/重开/返回）→ 失败结算（重试本关/返回选关）；关键状态均附图标＋文字（目标点金环＋「目标」标签、死角红框＋「死角」标签），不只靠颜色区分；Esc 暂停面板含继续/重置本关/返回选关/设置；窗口失焦自动暂停（F10 与 I05 一致）。

## 生成任务明确性补充（2026-10-12）

> 本补充只约束游戏生成输入，不引用 rubric。所有生成器必须以本文件规则和下列 JSONL 任务为准；未列出的装饰细节可以自由发挥，但不得省略已列资产或生命周期。

### 故事与流程最低合同
- **玩家身份与当前冲突**：以 §1、§8 的角色/世界/冲突为唯一叙事入口；开局必须让玩家知道“我是谁、现在要解决什么问题”。
- **阶段性目标**：必须有可操作的阶段目标、至少一次状态变化/升级，并在 §7 的胜利、失败、重开入口中闭环；不能只生成一个无结果的场景演示。
- **结果承接**：胜利/失败都要有明确结果文案或演出，并回到可重开、暂停或标题入口；视频、音频和 VFX 不得推进未完成的玩法状态。

### 生成任务清单（JSONL 冻结口径）
- scene：1 个；必须生成连贯可游玩的空间，不得出现下半部文字、拼贴面板、物体 lineup 或 UI。
- object：3 个（text-to-3D 1，image-to-3D 2）；object 任务资产为：sorting_robot, prop_crate, goal_marker。每项只允许一个物体；组合物必须拆成独立任务。
- motion：1 个；覆盖动作：sort_and_place。
- video/audio/mechanic/UI：分别为 2/6/1/1 个任务；若某项为 0，只能是本案例明确的 N/A，不得默默遗漏。

### Video / motion / audio 生命周期
- Video 每项必须写清 `trigger`、`start_condition`、`duration_sec`、`skippable`、`skip_behavior`、`end_condition` 和进入的下一个游戏状态；播放期间不得偷偷消耗计时或改变战斗/任务数值。
- Motion 每项必须写清 `source_asset`、`trigger`、`start_condition`、`duration_sec`、`loop`、`end_condition` 和 `cancel_behavior`；动作要与对应输入/机制事件绑定，不可只写“walk animation”。
- Audio 每项必须写清触发事件、时长、`loop`、`stop_condition`、优先级和 ducking；关键命中/提示音必须与事件帧同步，暂停/结算时按 §9 处理。

### Mechanic / UI / 游玩手感
- Mechanic JSON 与 §1–§7 配对：每个输入都要有 precondition、state_change、feedback、next_state；必须说明失败/禁用分支。
- UI JSON 与 §9/F10 配对：HUD、菜单、结算、暂停、错误/禁用态要有 state binding；关键状态不能只用颜色表达。
- 手感冻结：相机跟随/构图、FOV、碰撞/遮挡、镜头调整与镜头震动必须在 §9 说明；震动反馈必须写明触发、强度和持续时间，并提供关闭设置且不改变判定。

### VFX 时机合同
每个特效必须写清 `trigger event`、预备/前摇、active window、持续时间、结束条件、被打断/取消条件，以及和相机震动、音效、UI 的同步关系；命中特效、失败特效、胜利特效不能只写“有粒子”。
