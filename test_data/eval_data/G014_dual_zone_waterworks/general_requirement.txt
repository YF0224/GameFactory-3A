## 1. 定位与完整流程 [S01–S06]

- S01 类型：双客户端信息不对称协作平台（Platformer / Runner），1 个权威 host 会话＋2 个独立客户端进程各接 1 名维护员角色。本测例包含的能力：分端信息不对称探索、压板-门/拉杆-闸门互补联动、文字 ping 协作沟通、单端独立重生与共享检查点、闸门防夹、断线安全结束、开场/协作事件/结算视频、协作手感演出层。
- S02 核心循环一句话：各自探索 → 机关互补触发（对端开路）→ 联动开门 → 共同推进 → 双端汇流。
- S03 流程：开始界面（创建/加入会话、双端 ready）→ 同步开局（首次进入前播 C01）→ 水闸区（客户端A）与泵房区（客户端B）双端并行推进 → 两区机关链完成解锁汇合终点区 → 双端齐达 GOAL 触发 joint_win → 结算（面板前播 C03）→ 重开或返回。
- S04 最低完整流程：会话创建与加入、双端就绪同步开始、A 站 PLATE_W1 开 GATE_B1 且 B 通过、A 站 PLATE_W2 开 GATE_B2 且 B 通过、B 扳 LEVER_P1 开 GATE_A1 且 A 通过泄洪水道、双端进入汇合终点区、结算界面、重开必须全部存在且有真实入口。
- S05 失败恢复入口：单端坠落→仅该端独立重生于本端最近已点亮检查点（本局内，2 秒重生动画）；1200 秒超时或机关死锁→失败结算；断线→安全结束为 incomplete（不判 PASS 不判负）；任一端 Esc/失焦→全局暂停；结算界面一键重开。
- S06 本局耦合边速览：E01 压板系统→门禁系统（对端门状态即时联动，事件时序 oracle）。

## 2. 完整核心循环与阶段 [S07–S12]

- S07 启动与会话
  - input：系统启动加载完成（触发方：系统）；host 创建会话、第二客户端加入，双方按 Enter 就绪（触发方：玩家）
  - precondition：构建可启动且资源加载完成；两客户端就绪前不推进模拟（AUD10）
  - state_change：相同 session_id、角色 A/B 绑定完成 → 进入「同步开始」；首次开局按 §10 C01 播放开场视频
  - feedback：会话界面显示双端 ready 状态；日志带 client_id、input_seq、state_seq
  - next_actions：双端 ready 后同时进入「并行推进」
  - outcome：无跨局状态写入；断线在就绪前→安全结束
- S08 并行推进（水闸区A／泵房区B）
  - input：移动 A/D、跳 W/Space、下蹲 S、交互 E、ping Q、Esc 暂停（触发方：玩家）；机关由双端位置与交互触发（触发方：系统）
  - precondition：双端已同步开始且非暂停/结算/视频
  - state_change：按 §6 M01–M03 结算每次输入；压板/拉杆/门状态、检查点点亮、坠落计数、双端位置实时更新
  - feedback：按 §9 F05（压板光效、拉杆脉动、水线开门、ping 标记、重生溶解）
  - next_actions：三组机关链完成 →「汇合推进」；任一端死亡 → M03 独立重生；机关死锁/超时 →「失败结算」
  - outcome：按 §7 V01/V02 判定；同帧失败优先（G06）
- S09 汇合推进（汇合终点区）
  - input：同 S08（触发方：玩家/系统）
  - precondition：两区机关链已完成（GATE_A1 已被 B 通过、GATE_B1/B2 已被 A 通过）
  - state_change：双端沿汇流走廊推进；单端在终点格仅产生 waiting 事件不结算
  - feedback：同 S08；先到端 HUD 显示「等待队友」
  - next_actions：双端 in_goal 同时为真 →「胜利结算」
  - outcome：joint_win 结算（评级分按 G02）
- S10 胜利结算
  - input：Enter=重开 / Esc=返回（触发方：玩家）
  - precondition：V01 成立（双端齐达 GOAL）
  - state_change：进入「胜利结算」；面板出现前按 §10 C03 播放结算视频胜利意象（每局一次）
  - feedback：结算面板显示评级分、坠落总次数、用时（G02 公式）
  - next_actions：重开（全量重置）或返回标题
  - outcome：无跨局状态写入
- S11 失败结算
  - input：Enter=重开 / Esc=返回（触发方：玩家）
  - precondition：V02 成立（1200 秒超时 timeout 或机关死锁 deadlock）
  - state_change：进入「失败结算」；面板出现前按 §10 C03 播放结算视频失败意象（每局一次）；断线安全结束显示 incomplete，不进入本结算
  - feedback：失败面板注明「超时」或「机关死锁」原因
  - next_actions：重开本局
  - outcome：全量重置
- S12 暂停
  - input：任一端 Esc 或窗口失焦（触发方：玩家/系统）
  - precondition：处于游玩状态
  - state_change：**全局暂停**——两端模拟时间冻结（含门保持窗与超时计时）；恢复需双端确认继续（AUD12）
  - feedback：两端暂停面板（继续/重开/返回/设置）；失焦端标记等待确认
  - next_actions：双端确认 → 回到游玩
  - outcome：恢复后状态逐字段一致；不补发暂停期间的输入

## 3. 数值口径与全局规则 [G01–G06]

- G01 统一刻度：1 格＝1 米；模拟时间毫秒；事件时间戳一律取权威 host 单调模拟钟，双端日志按事件序对齐（client_id、input_seq、state_seq）。
- G02 数值与公式：双人基础移动（AUD14）——横向 4 m/s，跳跃峰高 1.5 m、总时长 0.8 秒（无二段跳），站立碰撞高 1.8 m、下蹲 1.0 m；跳跃与下蹲互斥。结算评级分＝1000−30F−2×floor(M)（F=双端坠落总次数、M=用时分钟）。独立 oracle 数例：F＝4、用时 14 分 20 秒 → floor(M)＝14 → 1000−120−28＝**852**。联动延迟窗口：plate_pressed 到对端 gate_opened 的差 **0≤Δt≤200 ms**（zkx 裁决口径，含同帧）。
- G03 关卡与机关：协作机关 3 组（压板-门×2：PLATE_W1→GATE_B1、PLATE_W2→GATE_B2；拉杆-水道闸门×1：LEVER_P1→GATE_A1）；共享检查点 4 个（CP1 水闸区入口、CP2 水闸区机关后、CP3 泵房区入口、CP4 泵房区机关后）；汇合终点区 1；坠落谷与急流障碍若干；ping 标注图标 1 套。机关路径须在 G02 动作边界内可达（AUD14）。
- G04 随机流：fixed_seed=1014 决定机关布置候选与重生点微调；一切随机消费点先注册后取用，双端共享同一随机流以保证复现一致。
- G05 暂停与输入时钟：任一端 Esc/失焦→全局暂停（两端冻结）；恢复需双端确认；网络时延采用同一 host 单调时钟的接收/广播记录，不用暂停的模拟钟计算；输入延迟用单调实时时钟测量。菜单与暂停阻断玩法输入。
- G06 失败、死锁与同帧裁决：整局超时 **1200 秒**→timeout；机关死锁＝同一**尚未完成且双端都处于可操作状态的当前机关** 180 秒内无状态变化且双端无新触发（任何新触发重置计时，AUD13）→deadlock；双端同时死亡不判负、各自独立重生；1200 秒/死锁与 joint_win 同帧 → **失败优先**。先检查失败再检查成功（AUD01）；结算只触发一次并锁定玩法。

## 4. 操作与输入 [I01–I07]

- I01 键位（两客户端同构）：移动 A/D，跳 W 或空格，下蹲 S，交互 E（拉杆按住拉、松开释放；检查点点亮），文字标注 ping Q，暂停 Esc；结算界面 Enter＝重开。角色进入压板判定格即触发，无需按键。
- I02 输入语义边界：忙时（重生 2 秒回卷动画）丢弃输入且无位移副作用；死亡瞬间的输入不入队；越界与组合冲突输入直接拒绝；被拒绝输入不产生任何状态变化。
- I03 面板内输入走独立通道：暂停/结算面板打开时移动与交互输入被拒绝，面板操作独立，关闭后恢复；同帧多个互斥动作按 I01 列举顺序取首个，重复按下不叠加。
- I04 输入优先级：暂停与结算状态阻断全部玩法输入；同帧多输入按 §6 各机制声明的顺序结算（AUD01 事件顺序：先暂停/退出→有效输入→模拟与机制→占用迁移→先失败后成功→故事/HUD/反馈）。
- I05 焦点与失焦：点击画布捕获输入焦点；面板层阻断点击穿透；**任一端失焦即全会话暂停**（AUD12/G014 口径），恢复需双端明确继续，不补发失焦期间输入。
- I06 UI 必显状态：本端角色状态、当前联动机关状态（对端门开闭）、已点亮检查点（双端共享进度）、本端坠落计数、门保持窗剩余时间、ping 标记、会话状态（就绪/等待/断线）、局时。
- I07 输入延迟目标：每类有效输入 ≥30 次采样，按键到本地状态确认 P95≤100ms；跨端联动完成（plate_pressed→gate_opened）≤200ms（FEEL03，与本地延迟分开记录，不混同）。

## 6. 机制系统 [M01–M03]

- M01 信息不对称与 ping 协作（主机制）
  - input：双端分离视角（客户端A＝水闸区，客户端B＝泵房区）；Q 发文字标注（触发方：玩家）
  - precondition：双端处于游玩状态
  - state_change：一端可见的机关线索与开关对另一端隐藏，各端可见集 Vis(A)/Vis(B) 在机关线索层不相交；协作沟通以 ping 标注替代语音；ping 双端广播（世界坐标锚定）
  - observable：可见对象差分流水 diff(Vis(A),Vis(B))、ping 广播事件（含位置与 owner）
  - invalid_case：隐藏线索未揭示前不得通过对端 UI 泄露；非法/忙时输入拒绝且无副作用
  - recovery：ping 10 秒后淡出可重发；无失败态
- M02 压板-门联动与闸门防夹（主机制）
  - input：角色进入压板判定格（PLATE_W1/W2）或 E 按住拉杆（LEVER_P1）（触发方：玩家）
  - precondition：处于游玩状态；拉杆需按住持续生效
  - state_change：压板——站立期间保持对端门开（plate.state idle→pressed）；离板时启动 **10 秒保持窗**再回落，保持窗内再踩取消关门倒计时（AUD11）。拉杆——E 按下拉住（lever.unpulled→pulled）对端 GATE_A1 开，松开立即释放、即时门随释放关闭。门关闭时若角色重叠 → 角色退回门前最近安全点，**不把角色夹入墙**（AUD11 防夹）；压板/拉杆保持期间触发方死亡 → 物理占用释放，门按原释放策略变化（AUD12）
  - observable：联动因果事件对 plate_pressed(t0)→gate_opened(t1) 且 0≤t1−t0≤200ms；保持窗事件 gate_holding/gate_closed；防夹退回事件（含安全点坐标）；触发归属 switch_triggered(owner)；死亡释放占用事件
  - invalid_case：超时/无效交互拒绝且无副作用
  - recovery：门回落后可重新触发；防夹退回不判死
- M03 独立重生与共同通关（主机制）
  - input：坠落谷/急流死亡判定；双端各自抵达 GOAL（触发方：系统/玩家）
  - precondition：处于游玩状态
  - state_change：单端死亡 → 仅该端 respawn 至本端最近已点亮检查点（2 秒重生动画），机关完成进度与对端不回退（AUD12）；检查点点亮进度为双端共享全局状态（过机关者点亮，不随单端死亡回退）；双端 in_goal 同时为真 → joint_win 结算；单端在终点仅产生 waiting 事件
  - observable：respawn 事件（owner 与 checkpoint_id）、joint_win 事件、waiting 事件
  - invalid_case：重生动画期间输入丢弃；结算后再触发判定被拒绝
  - recovery：重开为最终出路；断线→安全结束 incomplete

系统耦合边（玩法必需、可复现）：

- E01 from_system=压板系统 → to_system=门禁系统；changed_state=plate.idle→pressed 时对端 gate.closed→open（保持型站立保持＋离板 10 秒保持窗／即时型释放回落）；验证方式=探针在 state_before=gate.closed 下令客户端A 角色进入 PLATE_W1，记录双事件时间戳并断言 state_after=gate.open 且 0≤t(gate_opened)−t(plate_pressed)≤200 ms（联动事件时序 oracle；拉杆 LEVER_P1 复用同一门禁输入接口）；死亡解除占用后门状态变化单独取证。

## 7. 成功、失败与恢复 [V01–V06]

- V01 成功条件：双端角色 in_goal 同时为真 → joint_win 结算，评级分按 G02 公式。
- V02 失败条件：整局 1200 秒超时 → timeout；机关死锁（G06 口径）→ deadlock；两者与 joint_win 同帧失败优先。双端同时死亡不判负、各自独立重生；断线→安全结束 incomplete，不判 PASS 也不判负。
- V03 恢复语义：仅本局检查点——单端死亡仅该端 2 秒重生至**本端**最近已点亮检查点（安全出生锚点，AUD14）；检查点点亮进度双端共享、不随单端死亡回退；断线后重连按 incomplete 单独记录。
- V04 persistent_state：局内检查点点亮进度（双端共享）、机关完成状态与双端坠落计数；无跨局存档，重开全量清空。
- V05 persistent_state 生命周期：动作级即时结算；局级状态局内保留、重开清空；无跨局保留。
- V06 软锁与不可达处理：不设永久软锁——死锁计时（G06）确保 180 秒无进展触发明确失败而非无限等待；机关路径在 G02 动作边界内可达（AUD14）；防夹退回避免角色卡死；结算界面重开为最终恢复出路；不得把恢复入口缺失解释为正常失败。

## 8. 世界设定与创作基线 [W01–W08]

- W01 世界与时代背景：两端同一条水线——季风年久失修的高山水利枢纽，远程检修队承接的最后一单；水闸区与泵房区被山体隔断，只有靠对端配合才能放行彼此的水路。
- W02 场景所在地：分离的双区设施（上游水闸区＝泄洪水道与压板平台；下游泵房区＝拉杆机房与双门走廊）与汇合终点区（双端汇流的检修终点台）。
- W03 玩家身份与当前任务动机：两名水利检修员 A/B，各守一区；动机是在 1200 秒检修窗口内互通信息（ping 标注）、同步打开终点水道，共同抵达汇合终点。
- W04 失败代价与结局表达：失败=超时或机关死锁，检修记录终止（C03 失败意象）；成功=双端汇流、终点台点亮（C03 胜利意象）；断线=本班记录 incomplete。
- W05 叙事来源：压板=配重检修平台；拉杆=泄流阀杆；闸门=泄洪水道/泵房双门；检查点=检修灯站（过机关点亮）；急流=检修期开闸放水的失控水流。全部原创。
- W06 视觉风格与色彩材质：工业水利风；主色=钢青 #4A6F8C、安全橙 #E4762C、水线蓝绿 #7FD8E8、混凝土灰 #9AA3AB、警示黄 #E8C559；材质为湿混凝土、防滑钢板、阀门黄铜与水流。
- W07 环境氛围与声音语言：水流与机房低鸣为底；音效语言为「压板下沉＋门铰上扬＋拉杆机械＋ping 提示＋重生溶解」，全部音效按 §9 F06 冻结清单交付；混音优先级：deadlock/timeout 警报 ＞ 门与机关反馈 ＞ ping ＞ 环境水流。
- W08 故事表达方式：开场视频（C01）交代双区隔断与汇合目标 → 协作机关事件视频（C02）承载联动配合的过程叙事 → 结算视频（C03）收束；叙事提示不阻断控制、不改变数值；提前失败允许直接进入失败结局，不强行播放未发生的成功节拍。

## 9. 演出、镜头与反馈 [F01–F10]

- F01 视角与镜头：双端各自跟随角色（侧视跟随，前方安全区 ≥ 屏宽 35%）；机关触发时只对本端做轻微镜头提示（门开轻微推近 0.05s），双端视野不得被强制拉走（FEEL01）；相机重置仅在明确切场/复位时，不穿过遮挡体或泄露视野外实时信息。
- F02 关键操作镜头变化：对端门联动开起 0.05s 轻推；本端重生淡入；设置提供「镜头震动开/关」与「减少动态效果」（关闭抖动与剧烈旋转、保留状态提示；关闭不影响判定与数值）。
- F03 输入与延迟：见 I07（本地 P95≤100ms；跨端联动 ≤200ms 分开记录）；顿帧不改变计时口径。
- F04 环境常驻效果：泄洪水道水流、泵房蒸汽、检查点灯站呼吸光、ping 标记浮现。纯表现层，不参与判定。
- F05 事件反馈表（事件 → 画面表现 → 音效 → 结束条件，全部冻结需求）：

| 事件 | 画面表现 | 音效 | 结束条件 |
|---|---|---|---|
| 压板踩下（plate_glow） | 压板下沉＋面板光圈 | 压板下沉音 | 离板 |
| 拉杆拉住（lever_pulse） | 拉杆后仰＋阀杆脉动 | 拉杆机械音 | 松开 |
| 对端门开启（gate_open_waterline） | 门上抬＋水线光带流过 | 门铰上扬音 | 保持窗结束/即时关闭 |
| 门保持窗倒计时 | 门框黄条倒数 | 无 | 窗结束回落 |
| 门防夹退回 | 角色退回门前＋黄框提示 | 短促警示音 | 退回完成 |
| ping 标注（ping_marker） | 世界锚定图标双端可见 | ping 提示音 | 10 秒淡出 |
| 单端死亡占用释放 | 门沿原释放策略回落 | 门回落音 | 门状态稳定 |
| 重生（respawn_dissolve） | 本端角色溶解淡入＋检查点亮起 | 重生音 | 玩家可控即停 |
| 双端 waiting | 先到端「等待队友」图标 | 无 | 对端到达或重开 |

- F06 关键音效清单（one_shot 9 条＋环境循环 2 条，全部冻结需求）：压板下沉音、拉杆机械音、门铰上扬音、门回落音、ping 提示音、重生溶解音、联合胜利音、死锁警报音、超时低音；环境循环：泄流水流（常驻，暂停静音、结算淡出 0.5 秒，接缝无爆音）、机房低鸣。无配音需求。震动事件到调度日志 ≤50ms，日志含 source_event_id/单调时间/amplitude/duration_ms/channel/device_available；无震动硬件时验证调度与禁用行为，不声称物理马达已震动。
- F07 VFX 信息性与遮挡约束：压板光圈、门保持窗黄条、检查点亮起、ping 标记为信息类 VFX，必须清晰可辨；粒子不遮挡 HUD 与机关判定区；隐藏线索（对端机关信息）不得被特效泄露；非结算单个全屏遮挡 ≤0.5 秒。
- F08 音画同步：压板音与下沉同帧；门铰音与上抬同帧；ping 音与标记浮现同帧；重生音与溶解同帧。
- F09 屏幕震动：仅核心受击级事件轻微抖动（≤ 画面高度 1.5%）；暂停/结算/重开取消未结束的震动与特效，不影响判定；设置可关闭（FEEL04）。
- F10 前端界面：标题（创建会话/加入/退出）→ 会话就绪（双端 ready、session_id 显示）→ 检修 HUD（I06 全项）→ 结算面板（评级分/坠落/用时/原因/重开/返回）→ 暂停面板（继续/重开/返回/设置，双端确认继续）；关键状态图标+文字并用；任一端失焦自动全局暂停；叙事节拍提示不阻断控制。

## 10. 过场视频 [C01–C03]

- C01 同一条水线（Opening，5 秒，1280×720@24fps）
  - 触发时机：双端 ready 后、同步开局之前，每局一次
  - 内容与角色场景：航拍山体隔断的水利枢纽——上游水闸区与下游泵房区的两盏检修灯同时亮起，镜头沿水线推向汇合终点台
  - 资产对应：维护员、双区设施与游戏内模型/贴图同源设计
  - 可跳过：Enter/Space 或跳过按钮 → 直接同步开局；自然播完 → 同步开局
  - 状态一致：跳过与自然播完后初始状态 hash 相同；播放期间不推进任何游戏计时（AUD03）
- C02 对端开路（Event，5 秒，1280×720@24fps）
  - 触发时机：每局首次成功联动开门（任一组压板-门或拉杆-闸门首开）时，每局一次
  - 内容与角色场景：分屏对切——A 端踩下压板的同时 B 端门铰上扬、水线光带流过门洞，两端维护员隔屏对望；ping 标注在两帧间穿针引线
  - 资产对应：维护员、压板、门与游戏内模型同源
  - 可跳过：Esc/Enter 跳过 → 直接继续推进（门保持窗状态保持）；自然播完 → 继续推进
  - 状态一致：播放期间模拟时间冻结（含门保持窗与超时计时），播放结束瞬间按冻结前状态恢复
- C03 汇流或终止（Ending，6 秒，1280×720@24fps，胜负共用双意象）
  - 触发时机：V01 或 V02 成立、结算面板出现之前，每局一次
  - 内容与角色场景：胜利意象=双端维护员在终点台并肩、双灯同亮、汇流光带贯穿全图；失败意象=警示灯闪烁、水线光带熄灭、检修记录合上注明原因
  - 资产对应：维护员、终点台、灯站与游戏内模型同源
  - 可跳过：Esc/Enter 跳过 → 直接进入对应结算面板；自然播完 → 进入对应结算面板
  - 状态一致：仅在真实 V01/V02 后触发；播放期间不推进任何游戏计时

## 生成任务明确性补充（2026-10-12）

> 本补充只约束游戏生成输入，不引用 rubric。所有生成器必须以本文件规则和下列 JSONL 任务为准；未列出的装饰细节可以自由发挥，但不得省略已列资产或生命周期。

### 故事与流程最低合同
- **玩家身份与当前冲突**：以 §1、§8 的角色/世界/冲突为唯一叙事入口；开局必须让玩家知道“我是谁、现在要解决什么问题”。
- **阶段性目标**：必须有可操作的阶段目标、至少一次状态变化/升级，并在 §7 的胜利、失败、重开入口中闭环；不能只生成一个无结果的场景演示。
- **结果承接**：胜利/失败都要有明确结果文案或演出，并回到可重开、暂停或标题入口；视频、音频和 VFX 不得推进未完成的玩法状态。

### 生成任务清单（JSONL 冻结口径）
- scene：1 个；必须生成连贯可游玩的空间，不得出现下半部文字、拼贴面板、物体 lineup 或 UI。
- object：7 个（text-to-3D 5，image-to-3D 2）；object 任务资产为：maintenance_worker, pressure_plate, valve_lever, linked_gate, shared_checkpoint_lamp, rush_riverbank_module, convergence_goal_platform。每项只允许一个物体；组合物必须拆成独立任务。
- motion：5 个；覆盖动作：move, jump, crouch, interact, respawn。
- video/audio/mechanic/UI：分别为 3/12/1/1 个任务；若某项为 0，只能是本案例明确的 N/A，不得默默遗漏。

### Video / motion / audio 生命周期
- Video 每项必须写清 `trigger`、`start_condition`、`duration_sec`、`skippable`、`skip_behavior`、`end_condition` 和进入的下一个游戏状态；播放期间不得偷偷消耗计时或改变战斗/任务数值。
- Motion 每项必须写清 `source_asset`、`trigger`、`start_condition`、`duration_sec`、`loop`、`end_condition` 和 `cancel_behavior`；动作要与对应输入/机制事件绑定，不可只写“walk animation”。
- Audio 每项必须写清触发事件、时长、`loop`、`stop_condition`、优先级和 ducking；关键命中/提示音必须与事件帧同步，暂停/结算时按 §9 处理。

### Mechanic / UI / 游玩手感
- Mechanic JSON 与 §1–§7 配对：每个输入都要有 precondition、state_change、feedback、next_state；必须说明失败/禁用分支。
- UI JSON 与 §9/F10 配对：HUD、菜单、结算、暂停、错误/禁用态要有 state binding；关键状态不能只用颜色表达。
- 手感冻结：相机跟随/构图、FOV、碰撞/遮挡、镜头调整与镜头震动必须在 §9 说明；震动反馈必须写明触发、强度和持续时间，并提供关闭设置且不改变判定。

### VFX 时机合同
每个特效必须写清 `trigger event`、预备/前摇、active window、持续时间、结束条件、被打断/取消条件，以及和相机震动、音效、UI 的同步关系；命中特效、失败特效、胜利特效不能只写“有粒子”。
